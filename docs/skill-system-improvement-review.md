# 技能系统设计检查与改进建议

状态：设计评审记录。本文依据当前玩法设计、架构文档与代码检查整理；提出的方向不是已经实现的功能。目标设计见 [技能系统完整机制设计](skill-system-complete-design.md)，实施策略见 [多战斗风格技能架构升级策略](combat-style-architecture-upgrade.md)。

## 一、评审结论

当前设计符合「易上手、通过组件组合创造技能」的基本方向，也已引入近战、远程、剑修等战斗风格。动作、属性和修饰的固定结构降低了学习门槛，共享状态、位置与死亡事件为技能间连锁提供了基础。

但目前仍应视为可运行的组合系统原型，不能仅凭理论组合数或自动化测试证明它已具备大量多样、具有涌现性的 build。动作替换、剑修的玩法身份、跨技能互动及玩家是否理解因果，需要继续设计和试玩验证。

## 二、优先改进事项

### P1：允许玩家在一轮中替换动作

**现状与影响**：原型最多两个技能；技能槽填满后不再提供新动作，动作也不像属性和修饰那样可替换。玩家选择近战和远程后，即使发现更想尝试御剑或陷阱，也无法在同一轮直接转换。这限制了实验不同战斗风格与组合的空间。

**建议**：在槽位已满时，让新动作可以替换一个现有动作。选择前预览替换后的技能、移动偏好，以及原属性和修饰是否仍兼容；兼容组件保留，不兼容组件交由玩家决定如何处理，或进入有空间的备用栏。备用栏不足时明确展示后果，不静默丢弃。

动作替换需要明确原动作的去向、技能实例 ID 和冷却如何处理、已存在实体是否保留旧技能快照。建议延续既有原则：已发射弹体及已生成实体沿用创建时的计划，新施放使用新计划。具体库存和冷却规则应在实现前定稿。

**验收**：两个技能槽已满时仍能获得并选择可替换动作；兼容和不兼容组件处理均可预览；取消不改变构筑；替换后旧实体与新施放行为正确；备用栏满时无意外丢失。

### P1：验证并增强跨技能互动，而不是先堆组件数量

**现状与影响**：单技能一个属性、一个修饰，原型最多两个技能；当前主要共享反应为传火、导电和碎裂。它们能够产生配合，但尚不足以证明系统能持续创造大量具有不同因果链的 build。

**建议**：先以现有机制进行试玩，观察玩家是否主动创造「一个技能铺垫、另一个技能兑现」的配合。然后少量引入可跨多种动作使用的互动，例如消耗已有状态换取范围效果、将状态转移给其他目标。每种互动需要公开、可预测的条件和代价，不依赖大量隐藏的两两配方。

这不意味着必须立刻开放更多技能或多修饰槽。若两技能原型已有可理解的多样选择，再根据体验决定是否扩大容量。

**验收**：玩家能解释至少两种跨技能配合的因果；同一通用互动能服务不止一种动作；不同 build 在敌群、单体和移动目标场景中表现有可感知差异；没有无代价强化所有组合的必选组件。

### P2：让剑修拥有不止一种可识别打法

**现状与影响**：评审时剑修以环身御剑为起点，已具备飞剑主题，但剑气、穿敌、聚剑齐发和剑阵仍是探索方向。仅凭环绕飞剑尚不能认定剑修已有丰富的战斗风格。

**建议**：优先原型化两种改变战斗方式的方向，而不是只替换特效：

- **飞剑穿敌**：将环身护体转向沿路径攻击，强化直线覆盖。
- **剑阵**：将跟随角色的输出转向固定区域控制，形成站位选择。

分别确定它们是动作还是修饰，写清目标选择、持续时间、命中次数、代价和适用能力；尽量复用公共属性、状态和反应。御剑与分裂、穿透等组合只有在语义明确后才声明兼容。

**验收**：两种玩法在攻击区域、自动走位与优势场景上明显不同；玩家能从描述预测结果；加入后不复制火、冰、雷和反应结算代码。

### P2：修正无法由现有规则推导的构筑示例

**现状与影响**：「寒冷陷阱 + 穿透突进」示例称陷阱会减速并聚拢敌人，但寒冷只提供减速，基础陷阱没有默认聚怪；突进和穿透也属于后续内容。

**建议**：把示例改成「寒冷牵引陷阱 + 穿透突进」，前提是陷阱与牵引确认兼容；否则保留寒冷陷阱并删除聚怪描述。明确标注突进、穿透尚未实现，不把目标示例表述为现有玩法。

**验收**：每个示例都能逐项追溯到已定义的动作、属性、修饰和共享规则；未实现组合有清楚标记。

### P2：同步文档中的设计目标与实际规则

**现状与影响**：完整玩法文档允许传火跨敌人继续传播；当前实现同时设置传播代数上限。架构文档中也保留了一些旧系统待替换的历史表述，而新架构已有部分落地。如果不区分目标和现状，后续开发容易依据不同文档产生冲突。

**建议**：以完整玩法设计为目标规则，架构文档描述实现契约，实施策略记录阶段状态；对有硬上限的反应明确记录上限、是否向玩家展示以及测试方式。更新已过期的旧系统描述，但保留必要的迁移历史。实现发生变化时同步修改对应文档。

**验收**：三份文档对传火、致死反应、动作开放阶段、已实现范围及未定事项的描述一致；每项偏差有明确负责人或后续决策记录。

## 三、建议的验证顺序

1. 先统一现有文档及构筑示例，避免在不一致的规则上继续开发。
2. 设计并实现动作替换与兼容组件处理，验证一轮中能否从近战切换至御剑或陷阱。
3. 用现有两个技能槽测试跨技能配合、可读性和玩家自主发现过程；根据结果选择少量通用互动。
4. 为剑修制作一到两种不同的行为原型，验证它们与已有属性、修饰和共享反应的组合。
5. 根据试玩结果决定是否开放第三技能、增加修饰或扩展反应，不以理论排列数量作为唯一目标。

## 四、验证证据与限制

本次检查运行了 `npm test`，108 项测试通过；代码中已有飞弹、光环、冲击、挥斩、御剑和陷阱动作定义，以及四种战斗风格定义。测试能说明已有规则和部分边界受到覆盖，不能证明组合足够丰富、玩家理解因果、各种风格已经平衡。

建议的试玩记录包括：玩家首次完成组装所需步骤、能否预测组合结果、是否主动尝试跨技能配合、不同动作和修饰的选择率、不同敌群下构筑的表现，以及玩家是否能从画面或统计解释伤害来源。具体样本量、平衡阈值和性能预算应结合测试条件确定。

## 五、处理结果（2026-11）

| 建议 | 处理 |
|---|---|
| P1 动作替换 | 两技能槽已满后，新动作可替换现有动作。替换保留技能实例 ID、冷却与兼容属性/修饰；旧动作和不兼容组件进入备用栏；空间不足时拒绝并提示，不静默丢弃。候选会预览保留、移入与阻塞原因；旧实体保留创建时计划，新施放使用新计划。 |
| P1 跨技能互动 | 新增通用修饰 `引爆`：消耗目标全部状态，按层数在目标处造成范围伤害，冷却 ×1.2；同一施放只触发一次，且不重复触发自身。新增 `npm run synergy` 结构性观察工具，比较单技能与两技能构筑的反应、有效伤害与溢出伤害。 |
| P2 剑修身份 | 在御剑之外新增 `飞剑穿敌`（直线穿透、每目标最多命中一次、有限命中数）与 `剑阵`（固定区域、周期命中、持续与上限）。后续将剑修起始改为 `弧光飞剑`（中距离弧线、末段有限追踪、单目标拦截），环身御剑保留为可获取备选。它们复用属性、状态、反应和统一结算，不使用独立伤害规则。 |
| P2 构筑示例 | 将无法由现有规则推导的「寒冷陷阱 + 穿透突进」替换为「冰霜牵引陷阱 + 雷电剑阵」，并标注突进、穿透尚未实现。 |
| P2 文档同步 | 完整玩法文档新增当前实现范围与未实现项；架构文档更新动作/实体/修饰/动作替换与 `maxChain` 说明；升级策略记录阶段状态。评审文档保留为历史记录，处理结果见本表。 |

验证：`npm test` 138 项通过；`npm run build:check`、`npm run sim`、`npm run arena`、`npm run synergy`、`npm run preview` 均已运行。测试与工具仍不能替代真实试玩对可理解性、平衡和 build 多样性的判断。
