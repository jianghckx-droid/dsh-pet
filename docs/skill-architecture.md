# 技能系统架构设计

状态：第一版原型与多战斗风格架构升级已实现（2026-11）。模块划分、数据契约、动作生命周期、持续实体、移动决策与结算顺序按本文及 [多战斗风格技能架构升级策略](combat-style-architecture-upgrade.md) 落地；未实现范围见文末。数值仍为原型参数。

## 目标与边界

玩家将动作、属性和修饰组装为技能；不同技能通过共享状态和战场位置交互。运行时必须确定性、可测试、可存档；新内容优先通过注册定义接入，不为每种组合添加分支。特殊行为允许编写处理器，但不提供任意脚本或通用可视化编程语言。

保留现有项目无 DOM 的战斗模拟与客户端分离方式。现有 `arena.js` 混合了旧卡牌、战斗和抽卡逻辑，`rules.js` 包含旧属性和锁规则；它们是待替换的集成点，并非新规则的约束。渲染、进度、敌人及存档需要适配，不应直接读取旧卡字段。

## 模块与依赖

```text
内容定义 actions / elements / modifiers / statuses / reactions
                    ↓ 注册并校验
构筑 build → 编译 compiler → 不可变技能计划 SkillPlan
                                  ↓
战斗模拟 world → 调度 scheduler → 动作运行时 → 效果结算 resolver
                    ↑                    ↓              ↓
                  RNG/时钟         实体/空间查询    状态/反应/命令队列
                                                        ↓
                                               战斗事件与统计
                                                        ↓
                                                UI / 回放 / 模拟器
```

建议目录 `src/game/skills/`：`registry.js`、`compile.js`、`runtime.js`、`resolve.js`、`status.js`、`reactions.js`、`content/`。实体移动、碰撞、敌人 AI 留在战斗世界；UI 不参与裁决。客户端与模拟工具共用同一模拟实现。内容定义与表现资源通过稳定 ID 关联，不通过中文名称匹配。

## 数据契约

以下是示意数据，不是最终数值或 JavaScript API 的现有实现。

```js
// 可序列化的玩家选择；空槽使用 null。
const build = {
  version: 1,
  skills: [{ id: 'skill-1', action: 'projectile', element: 'fire', modifier: 'split' }],
  reserve: [],
};

// 动作由实现类型和参数描述；能力用于校验，而非判断具体 ID。
const projectile = {
  id: 'projectile', kind: 'action', handler: 'projectile',
  capabilities: ['hit', 'projectile', 'targeted'],
  params: { cooldown: 1, damage: 2, speed: 100 },
};
const fire = {
  id: 'fire', kind: 'element', requires: ['hit'],
  onHit: [{ type: 'applyStatus', status: 'burn', stacks: 1 }],
};
const split = {
  id: 'split', kind: 'modifier', requires: ['projectile'],
  transform: { type: 'splitProjectile', count: 2, damageScale: 0.5 },
};
```

注册表按类别保存定义并拒绝重复 ID、未知处理器、缺失引用、非法参数。构筑编译时验证槽位类型、能力要求、数量上限；失败返回可显示的结构化错误。编译生成含动作处理器、参数、命中效果、修饰及描述所需信息的 `SkillPlan`，运行时不再反复扫描构筑。定义不可变；冷却、投射物、状态层数等实例状态仅存在战斗状态中。

描述由同一份编译结果和本地化模板生成，保证数值来源一致；不能表达的组合在内容校验阶段暴露。能力集合初始限定 `hit`、`projectile`、`area`、`summon` 等；能力表示可承诺的行为，不只是标签。无意义或不支持的组合在界面禁用并说明原因。

## 运行模型与结算顺序

世界状态包含时间、随机数状态、稳定实体 ID、技能实例、实体位置与生命、状态、待处理命令及统计。`step(world, dt)` 仅使用输入状态和显式 RNG；相同初始状态、seed 和 dt 序列必须产生同一结果。使用固定模拟步长并持久化累积时间；同一时刻按实体 ID、技能实例 ID 和入队序号稳定排序。

每次固定步的顺序：推进时钟及已有状态计时 → 到期技能产生动作 → 更新投射物、区域及碰撞 → 按队列处理命中和后续命令 → 处理死亡与清理 → 输出表现事件。命中结算：

1. 校验来源和目标仍有效；确定命中快照及来源标识。
2. 按命令的伤害通道折算战斗属性：通用伤害加成 + 满足条件的伤害加成 → 逐命中判定暴击 → 得到最终伤害；记录实际伤害，生命降至零时标记待死亡，但保留该次命中的状态效果结算。
3. 应用属性效果与修饰生成的状态或位移命令；按确定顺序检查共享反应，产生后续命令。
4. 处理该命中的死亡：每个实体只触发一次死亡事件，读取死亡时状态快照，执行传火等反应；之后移除实体。
5. 后续命令按 FIFO 入队处理，不递归调用结算器。无效目标的命令安全跳过，已命中的死亡目标不能被再次命中。

每个命令携带 `eventId`、`rootEventId`、`sourceEntityId`、`skillInstanceId`、`targetId`、`tags`、`depth`；派生命令继承根事件与技能归因，增加深度。反应按显式优先级和稳定 ID 排序；同一事件对同一反应至多触发一次。设置每根事件的深度及命令数上限，并记录截断诊断；上限是安全护栏，不代替反应自身的终止规则。表现事件只读，禁止回调修改模拟状态。

战斗属性折算集中在 `src/game/attributes.js`，由公共入口调用，动作与实体不重复实现。伤害命令用 `payload.channel` 标注来源：`direct`（动作直接命中）与 `derived`（分裂 / 回响 / 引爆）参与逐命中暴击判定，`dot`（状态周期伤害）与 `reaction`（反应伤害）只吃通用与条件加成。元素标签继续来自技能内容，条件伤害按元素 / 标签 / 目标状态匹配，每条规则只结算一次。暴击使用从 seed 派生的独立 RNG 流，`battle.rng` 的刷怪与三选一序列保持不变。

## 状态与共享反应

状态定义包含 ID、层数上限、持续时间、重复施加策略、周期处理器和移除策略；实例记录层数、到期时间、下次跳动时间及来源。原型明确采用：灼烧重复施加增加层数并刷新整体持续时间；寒冷增加层数并刷新持续时间；充能为有限层数且可过期。具体上限和时长放配置。每种状态可替换策略，但必须由定义明确，不隐式继承。

反应订阅有限的语义事件（如 `statusApplied`、`hitResolved`、`entityDied`），读取快照后仅提交命令。初版规则：

- **传火**：带灼烧的敌人死亡时，按距离、再按实体 ID 选取附近有限目标并施加灼烧；传火产生的状态不直接触发死亡。
- **导电**：一次雷电命中对已有充能目标施加新充能后，消耗规定层数，向附近有限目标生成雷击；该雷击不施加充能，不再触发导电。
- **碎裂**：寒冷达到阈值的目标受到带 `heavy` 标签的命中后，消耗寒冷并产生范围伤害；碎裂伤害没有 `heavy` 标签，不再触发碎裂。

阈值、范围、目标数及数值由内容定义，不能靠递归副作用隐式决定。死亡目标仍完成本次状态施加，因此火焰致死命中可触发传火；这也应成为测试用例。

## 扩展方式

- 新动作：注册定义及动作处理器，声明真实支持的能力；处理器只通过世界接口生成实体或命中命令。
- 新属性：声明所需能力和命中效果；复用已有状态或新增状态定义及处理器。
- 新修饰：声明能力要求及编译期转换或指定阶段的行为；不得直接修改其他技能实例。
- 新反应：订阅语义事件，声明条件、消耗和产生的命令；注明来源标签与终止条件。
- 新敌人：通过统一的伤害、状态、移动和死亡接口参与战斗；不读取具体技能 ID。特殊抗性使用显式规则，并在 UI 描述。

例如增加毒属性，只需注册毒与其持续状态；若希望死亡传播，另注册反应。已有飞弹和光环只要具备 `hit` 能力即可支持它，无需新增“毒飞弹”“毒光环”的组合代码。新行为类型仍需实现处理器和测试，不能保证任何新创意都只改配置。

## 存档、兼容与生命周期

存档保存版本、组件 ID、技能实例 ID、槽位、备用栏和必要的战斗实例状态；不保存函数、注册表对象或编译结果。加载时迁移版本、校验 ID，再重编译。缺失或已移除的组件应产生可见提示并安全清空对应槽，避免整份存档无法加载；无动作的技能不运行。每个工作区三个槽位，槽位 1 沿用 `dsh.pet.v5.<workspaceKey>`，槽位 2/3 追加 `.slot2` / `.slot3`；大厅负责继续游戏、新游戏、读取、删除与手动保存，打开面板本身不写盘。

旧系统语义已舍弃，不应把旧卡牌、核心或属性硬映射为新组件。迁移时保留与新设计无冲突的工作区身份及用户设置；旧战斗构筑和旧进度的保留范围需在新成长系统确定后明确。迁移前先备份原存档，版本化新存档，避免覆盖后无法恢复。编辑构筑时在原子操作中校验并重编译；已发射实体保留发射时技能计划快照，新施放使用新计划，避免中途改装改变飞行中的效果。

## 验证与交付顺序

1. 先实现注册、构筑校验、编译和空槽行为；测试缺失引用、能力不匹配及描述与参数一致性。
2. 接入飞弹、火焰、灼烧，验证碰撞、持续伤害、死亡传火及伤害归因。
3. 加入光环、冰霜、雷电及修饰；覆盖多技能共享状态、消耗顺序、死亡同帧、目标失效、连锁上限。
4. 使用固定 seed 和输入重放比较完整状态与事件序列；验证不同帧率输入在相同固定步数下结果一致。
5. 接入升级选择、存档迁移、UI 与战斗统计；用模拟器观察输出、技能触发数量和事件预算，再进行侧栏视觉与可读性测试。

性能预算需在真实侧栏环境测量：限制投射物、召唤物、状态实例和每步命令数量；超限策略必须确定且可诊断，不能静默随机丢弃。数值平衡和敌人设计应由原型实测决定，而非由架构预先锁死。

实现时的明确取舍：

- **动作范围**：实现挥斩、飞弹、光环、冲击、弧光飞剑、御剑、飞剑穿敌、剑阵、陷阱 9 个动作；3 属性、5 修饰（含引爆）、3 共享反应、3 基础敌人。召唤、突进、生命属性、聚焦与第三个技能未实现。每个技能最多一个属性槽和一个修饰槽。
- **动作生命周期**：契约在 `actions/contracts.js`（校验 + 描述），运行时在 `actions/*.js`（`canCast` / `cast`），调度器只负责冷却与成功计数。未知处理器在注册/编译阶段失败，不静默回退成另一种动作。
- **持续实体**：飞弹、弧光飞剑、御剑、飞剑穿敌、剑阵、陷阱共用 `entities/` 生命周期分派，实体保存计划快照、生命周期与私有状态；同帧创建后同帧首次推进，遍历按 ID、候选目标按距离加 ID 排序。实体上限超限写入诊断。弧光飞剑还使用逐段扫掠，按最早交点、再按敌人 ID 结算路径拦截。
- **修饰阶段**：`compile` / `cast` / `onHit` / `onEnd` 阶段由 `modifiers/index.js` 声明；当前仍只开放一个修饰槽，但结算器不再按修饰类型写分支。
- **移动策略**：风格只提供默认 `approach` / `keepDistance` / `auto`；`movement.js` 每步统一选择站位，技能只提供 `movement.preferredRange`。位移请求按优先级、来源 ID、入队顺序裁决；首版未接入突进内容。
- **战斗风格**：风格只提供起始构筑、移动偏好与视觉主题。默认远程射手；近战、剑修、陷阱师按最高层解锁。切换风格会按新风格重开本轮，不隐式改写已保存构筑。战场面板只保留折叠的属性栏与构筑栏，不再显示风格栏与移动栏：风格在「新游戏」界面选择，移动策略跟随风格默认值。开发者调试开关 `dsh.pet.debug` 仅在 UI 层放宽选择门槛，核心 `isStyleUnlocked`、存档战绩与解锁记录不变。
- **技能数量**：最多 2 个技能、每个 3 个槽位、备用栏 3 格；属性/修饰替换采用原子顺序。两槽已满后新动作可替换现有动作：技能实例 ID 与冷却沿用，兼容属性/修饰保留，旧动作与不兼容组件必须进入备用栏；空间不足时拒绝替换并提示，不静默丢弃。
- **确定性**：`arena.step(battle, dt)` 只依赖输入状态与显式 RNG。客户端以 1/60 固定步长累积推进；同一 seed、同样步数得到同一状态与事件序列。
- **命令护栏**：命令深度上限 8，每根事件最多 96 条，每步最多 1600 条；超限写入 `battle.diagnostics`，不静默随机丢弃。
- **反应终止**：传火可以跨死亡事件连续传播，受 `maxChain`、目标数、层数与命令预算约束；导电雷击带 `noConductive` 且不施加充能；碎裂伤害没有 `heavy` 且带 `noShatter`。同一事件对同一反应至多触发一次。
- **致死命中**：先完成属性状态施加与本次反应检查，再标记待死亡；火焰致死可传火、雷电致死可导电、强力致死可碎裂。死亡统一在命令队列清空后结算，每个目标只处理一次。
- **伤害统计**：只记录有效伤害（不超过目标剩余生命），溢出伤害单独累计；技能、状态与反应分别归因。暴击次数记在 `stats.crits`，护甲减免量记在 `stats.mitigated`。
- **角色属性**：`attributes.js` 负责基础属性 → 战斗属性的固定换算（上限：护甲减伤 60%、攻击速度 100%、暴击率 100%）；每级 1 点自由分配，与每两级一次的技能三选一互不竞争；阵亡重试保留本轮属性点，通关重开或切换风格重置。存档从第 6 版起记录 `attributes` / `attributePoints`，没有字段的旧档按等级推算未分配点。
- **存档**：每工作区 3 个槽位。槽位 1 使用 `dsh.pet.v5.<workspaceKey>`，槽位 2/3 追加 `.slot2` / `.slot3`，活动槽位记录在 `.active`。存档保存风格、移动策略、构筑 / 层数 / 等级经验 / 待选升级 / 累计战绩与保存时间；打开面板不写盘，开始或手动保存后才写入。优先读 v5；没有 v5 才迁移 v4，构筑原样保留并补默认风格 / 移动策略；v3 只迁移累计战绩。修复 v5 前写对应槽位的 `.bak` 备份；删除槽位 1 时连同该工作区的 v4/v3 源档一起清理，避免删除后旧档复活。
- **大厅**：继续游戏读取当前自动保存槽位（标记丢失时取最近更新）；读取其他槽位会从该存档所在层开始并把自动保存切过去；新游戏只重置本轮，当前与目标槽位的累计战绩和风格解锁合并保留；删除当前槽位会放弃本轮并回到大厅。
- **描述一致性**：动作与修饰处理器提供描述数据，`compile.js` 用最终计划生成 `descriptionData` 与文本；测试断言结构化数值，不再依赖“描述里包含某个数字”的子串检查。
