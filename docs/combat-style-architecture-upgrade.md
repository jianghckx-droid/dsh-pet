# 多战斗风格技能架构升级策略

状态：阶段 0–3 已实现，阶段 4–5 部分实现（2026-11）。本文描述目标与实施顺序；已完成范围与剩余项见文末「实现状态」。玩法目标见 [技能系统完整机制设计](skill-system-complete-design.md)，既有技术方案见 [技能系统架构设计](skill-architecture.md)。如有冲突，应在实施前同步相关文档与实现。

## 1. 背景与目标

技能系统将支持近战、远程、剑修御剑、陷阱、召唤等战斗风格；后续还可能引入更多动作和技能组合。玩家仍以「动作 + 属性 + 修饰」组装技能，不需要操作程序。

目标是让新风格、新动作和新组件的改动集中在其自身：新动作复用统一命中、属性、状态、反应与统计；新属性不必分别修改每一种动作；新修饰通过明确的能力契约适用于多个动作。已有设计中的确定性模拟、快照、存档和可追溯反馈继续有效。

扩展性不等于所有新玩法都能只改配置。如果一种行为首次引入新的实体生命周期、碰撞方式或自主决策，仍需编写并验证通用行为；之后相同能力的内容应能复用它。也不要求所有动作和修饰都兼容，语义不清的组合应明确禁用。

## 2. 当前实现的限制

- `src/game/skills/runtime.js` 的动作分派和实体更新针对现有飞弹、光环、冲击实现；持续环绕的飞剑、陷阱和召唤物需要新的生命周期。
- `src/game/skills/compile.js` 的部分描述按现有动作与修饰分支生成；增加类型时需要同步检查描述逻辑。
- `src/game/skills/resolve.js` 中有按修饰类型的分支；修饰越多，命中结算越容易承担过多具体行为。
- `src/game/arena.js` 的移动距离由现有策略主导，尚不能根据近战、远程和混合构筑选择合适站位。
- 注册表、编译构筑、统一命中、状态与反应已提供复用基础，但不能据此认为任意新风格只需添加数据。

此前检查发现的传火、致死反应、备用栏和描述等问题应先修复并补测试，避免把现有错误变成新行为的共同基础。

## 3. 目标分层

```text
战斗风格：起始构筑、移动偏好、视觉主题
                 ↓
技能组合：动作 + 属性 + 修饰 → 构筑校验与技能计划
                 ↓
动作运行：施放、持续效果、命中与结束
                 ↓
通用战斗能力：实体、移动、碰撞、状态、反应、统一结算
                 ↓
表现与统计：描述、动画、事件、归因
```

依赖单向：风格引用组件；组件编译为技能计划；动作和实体通过战斗世界接口提交命令；表现层只消费结果。战斗核心不以「剑修」「射手」等风格 ID 判断伤害规则。

## 4. 战斗风格定义

风格提供起始构筑、默认移动偏好、解锁条件和视觉主题。它不拥有一套独立的战斗结算代码。

```js
// 示意：字段和参数需在实现时确定。
const swordCultivator = {
  id: 'swordCultivator',
  nameKey: 'style.swordCultivator.name',
  startingBuild: [{ action: 'orbitingSword', element: null, modifier: null }],
  movementPreference: 'mediumRange',
  visualTheme: 'sword',
};
```

只改变起始组件、移动偏好和表现的风格，原则上新增定义即可；如需独特行为，则另行实现可复用的动作或能力。风格解锁不应天然意味着基础数值更强。风格 ID 和组件 ID 使用稳定值，显示文本与本地化分离。

## 5. 动作接口与技能计划

动作提供一致的生命周期：**检查是否可施放 → 施放 → 推进持续效果 → 产生命中 → 结束和清理**。并非每个动作都需要每个阶段：挥斩可能立即结束，御剑和陷阱则创建持续实体。

动作处理器通过世界提供的有限接口查询目标、创建实体和提交命中，不直接修改其他技能或绕过统一结算。统一命中携带来源实体、技能实例、施放 ID、目标、效果和标签；属性、状态、反应及伤害归因由公共结算处理。

构筑编译时校验组件类别、动作能力与修饰要求，生成不可变技能计划。技能描述由同一计划和处理器提供的描述信息生成，不能对未知动作静默回退为另一种动作的文案。技能变更后，新施放使用新计划；已发射实体和延迟效果使用创建时的计划快照。

## 6. 持续战斗实体

飞弹、环绕飞剑、陷阱和召唤物都可能拥有位置、来源和生命周期，但行为不同。应提供小而明确的通用实体契约，而不是为未来所有能力预建大型框架。

| 能力 | 飞弹 | 御剑 | 陷阱 | 召唤物 |
|---|---:|---:|---:|---:|
| 位置和生命周期 | ✓ | ✓ | ✓ | ✓ |
| 移动或跟随 | ✓ | ✓ | 可选 | ✓ |
| 碰撞或触发范围 | ✓ | ✓ | ✓ | 可选 |
| 对同一目标的命中间隔 | 可选 | ✓ | 可选 | 可选 |
| 自主选敌 | 可选 | 可选 | — | ✓ |
| 产生统一技能命中 | ✓ | ✓ | ✓ | ✓ |

实体实例至少有稳定 ID、类型、来源、技能计划快照、生命周期和自身状态；实体处理器负责推进、碰撞结果和清理。实体上限、目标顺序、同目标命中间隔和超限诊断必须明确。状态更新、反应和伤害不在实体处理器内自行裁决。

例如御剑处理器生成环绕实体，实体维护角度和逐目标命中间隔，碰撞后提交普通命中；火焰、冰霜、雷电和共享反应继续通过统一流程执行。陷阱与召唤仍需各自首次实现触发及行为逻辑。

## 7. 修饰与能力契约

修饰根据明确能力声明兼容性，而不是匹配风格或动作名称。例如扩大要求可调整作用范围，穿透要求沿路径前进且能继续命中，牵引要求有效作用中心，回响要求可重复一次效果。

能力必须对应运行时真实承诺，不只是标签。修饰处理器只在约定阶段修改技能计划或生成后续命令；新增通用修饰不应要求逐个修改已有动作。能力不足时编译失败，升级界面不提供该组合并说明原因。

不同动作上的语义必须明确：例如「御剑 + 分裂」究竟增加飞剑，还是发出剑气，不能仅因都带有 `hit` 能力就默认兼容。先确定一致规则并提供可读描述，再声明支持；不为追求组合数量制造难以预测的效果。

## 8. 移动与自动决策

常规移动由独立决策层统一处理；技能提供有效射程、理想距离及接近需求，不直接争夺角色的常规移动控制。

- **接近**：偏向进入近战技能有效范围。
- **保持距离**：优先利用远程技能射程。
- **自动**：综合已装备技能的有效距离与敌人位置选择站位；具体权重由原型测试确定。

玩家可选择策略，风格只提供默认偏好。多个技能混用时由决策层做一次统一选择。突进等技能提交临时位移请求，由移动系统统一检查边界、落点和优先级；失败时的冷却处理必须明确。不得承诺「安全」而没有可测试的判定规则。

## 9. 扩展成本预期

| 扩展 | 预期工作 | 核心改动 |
|---|---|---|
| 复用飞弹的新射手风格 | 风格定义、起始构筑、资源 | 通常无需改战斗核心 |
| 新增同类属性或状态 | 定义、必要的状态处理器、描述和测试 | 不应逐个修改动作 |
| 新增通用修饰 | 修饰处理器、能力要求、描述和测试 | 不应逐个修改兼容动作 |
| 首次实现御剑 | 环绕实体、碰撞和命中间隔、表现及测试 | 需要新增行为能力 |
| 首次实现陷阱或召唤 | 各自生命周期、触发或自主行为、表现及测试 | 需要新增行为能力 |
| 基于已有御剑的新技能 | 组合已有行为、参数、属性和表现 | 通常无需修改战斗主循环 |

这些是验收目标，并非当前实现已满足的保证。

## 10. 分阶段实施与验收

1. **修复共同规则**：先修复已确认的传火、致死反应、备用栏与描述问题；补充边界测试，确保旧行为与目标设计一致。
2. **统一动作接口**：将现有飞弹、光环、冲击接入生命周期接口，保持行为和表现；同 seed、同输入的回归测试应可复现。
3. **抽出持续实体**：先迁移已有飞弹，再实现御剑环绕、碰撞和同目标命中间隔；统一生命周期、快照与上限诊断。
4. **独立移动策略**：实现接近、保持距离、自动三种策略；验证近战单技能、远程单技能和近远混搭不会相互抢夺控制。
5. **用不同形态验证**：加入挥斩与御剑，测试火冰雷、兼容修饰、共享反应和死亡边界；再加入陷阱或召唤，验证等待触发或自主行为确实能接入。
6. **内容扩展与体验验证**：接入风格选择、文案和特效；检查升级候选、存档迁移、统计归因、侧栏可读性和性能。

每个阶段完成后运行相关自动测试、构建检查及必要的交互验证。新增动作必须覆盖合法和非法组合、快照、目标失效、实体清理、确定性及上限。架构通过的标准是新增第二种同类内容时能复用已实现的能力，同时不会使既有组合回归。

## 11. 存档和兼容

存档保存版本、风格与组件 ID、构筑及必要的运行状态，不保存处理器函数。载入时校验并重新编译，未知组件安全降级并给出提示。旧存档迁移前备份；风格系统引入后，默认风格和已保存移动策略的迁移须明确。原有客户端与模拟器继续共用战斗规则，避免表现与数值模拟分叉。

## 12. 实施范围、基线与交付单位

本提案只改变技能与战斗风格相关架构，不以此为由重写敌人、层数、token 压力或所有 UI。当前客户端通过 `tools/build-client.mjs` 将 `src/game/` 内核生成到 `client.js`；新模块必须加入该构建流程，不能仅在源模块中工作，也不能手改生成段。测试和模拟器继续使用同一份源规则。

实施前运行 `npm test`、`npm run build:check`，记录结果；保存代表性固定 seed、构筑、固定步长及输入序列作为回归样本。记录初始攻击、命中、状态、死亡、伤害与升级选择事件；不要把现有已确认的错误冻结为正确行为。每个阶段可以单独合入：先增加接口和测试，再逐步迁移调用方，最后删除旧路径。每阶段通过验收后才能推进；遇到行为差异先判断是预期修复还是回归。

## 13. 目标目录与职责

下列文件名为建议的实施目标，可依据现有构建器约束调整，职责和依赖不能随之模糊。

```text
src/game/
  arena.js                 战斗步骤、敌人、世界状态编排
  movement.js              常规移动决策和位移请求裁决
  skills/
    registry.js            内容定义与处理器契约校验
    compile.js             构筑校验、不可变计划、描述数据
    runtime.js             技能冷却和动作调度
    resolve.js             命中、伤害、状态与命令队列
    draft.js               候选和装配
    actions/               projectile、aura、impact、swing 等处理器
    entities/              生命周期分派、projectile、orbitSword 等处理器
    modifiers/             修饰编译与运行阶段处理器
    content/               数据定义及战斗风格目录
```

避免循环依赖：内容定义不导入运行时；编译器读取定义与能力契约；动作及实体使用世界接口；结算器不导入具体动作。处理器表与内容校验共用同一来源，避免只在字符串白名单登记却没有实现。静态导入和明确注册优先，确保单文件构建能发现所有模块；不引入运行时动态脚本加载。

## 14. 具体契约

### 14.1 构筑与计划

保持构筑只包含版本、技能实例 ID、动作/属性/修饰 ID 和备用栏；风格与移动偏好放在账户/本轮配置，不以风格隐式覆盖已保存构筑。校验稳定 ID、类别、槽位数量、引用、处理器和能力；错误返回 `code`、`path`、`message`。构筑无效不得部分应用；已知损坏存档走修复流程并提示。

技能计划至少包含 `skillId`、动作处理器 ID、只读动作参数、能力集合、属性效果、已编译修饰、移动提示和描述数据。描述从最终参数生成；不可识别处理器或无法描述的组件在注册/编译时失败。不得只靠检查描述中是否包含某个数字来证明文案正确。

### 14.2 动作和世界接口

下列为伪类型，具体 JS 导出可调整；所有状态变化仍通过模拟器统一调度。

```text
ActionHandler = {
  validate(def) -> errors,
  describe(plan, locale) -> description,
  canCast(context, skillState, plan) -> boolean,
  cast(context, skillState, plan) -> { accepted, commands },
}
Context = { time, rng, actorId, queryTargets, spawnEntity, enqueueHit, emitVisual }
```

`canCast` 无副作用；`cast` 成功才启动冷却并增加施放计数，失败时保持就绪，下一固定步重试。`commands` 的边界须统一：实现可选择直接调用受限 context 或返回命令，但同一处理器不能混用两种方式产生相同效果。处理器不直接改敌人生命、状态或其他技能；`emitVisual` 不能反向影响模拟。

调度顺序明确为：输入与时间 → 状态计时 → 常规移动及敌人移动 → 技能施放 → 实体推进与碰撞 → 延迟命令 → 命中/反应/死亡处理 → 敌人攻击 → 胜负检查。实际迁移如需调整顺序，应先增加行为测试并说明玩家可见差异。

### 14.3 实体契约

实体数据包含 `id`、`kind`、`ownerId`、`skillInstanceId`、`castId`、`planSnapshot`、位置、剩余生命周期和类型私有状态；不得保存函数。处理器包含创建校验、固定步推进、碰撞处理和清理；新实体在创建帧何时首次推进必须固定并测试。遍历和碰撞候选以稳定 ID 或明确的距离加 ID 排序，不能依赖偶然的数组顺序。

环绕飞剑的实例保存角度、半径、角速度及目标 ID 到下次允许命中时间的映射；目标失效时移除对应记录，实体结束时清理全部记录。飞剑每次碰撞使用发射时计划提交命中，不直接附加灼烧等状态。先保留原飞弹追踪、射程和销毁语义，待独立设计后再调整。

### 14.4 修饰与能力

将修饰分成可明确排序的阶段：编译参数、施放、命中后、结束。每阶段使用处理器注册表，定义优先级和稳定 ID；当前每个技能只有一个修饰，也应明确未来多修饰的顺序，但本次不开放多修饰。运行时处理器仅生成受控命令；重复效果带来源与终止标签，无法无限自触发。

能力定义应描述可执行行为和必需参数，例如 `area` 代表可读取和调整半径，`path` 代表可报告移动路径及后续命中；仅有 `hit` 不代表支持穿透或环绕。注册时校验处理器承诺，编译时校验组件需求；无法证明的组合默认拒绝。已有 `targeted`、`area` 等定义在迁移时逐项核对，避免直接改变现有合法组合。

### 14.5 移动与位移

决策输入为宠物与敌人的只读快照、策略、已装备技能的移动提示；输出为期望移动方向或目标点，不直接施放技能。近战建议距离应由动作数据提供；自动策略以确定性方式汇总有效距离，并在无敌人时回到指定区域。所有并列目标按 ID 打破平局。

位移请求包含来源、起点、目标方向/距离、优先级和失效条件；由移动层限制场地边界并一次性裁决。同一步多个请求按优先级、来源 ID、入队顺序裁决。首版只实现可测试的场地内落点，不宣称已具备完整危险评估。位移失败不消耗冷却；已有技能动作不引入位移，故不改变现有行为。

## 15. 分阶段实施清单

### 阶段 0：修复和建立基线

1. 修复传火能否跨死亡事件传播；使用状态持续、目标数和命令预算约束，增加三名连续死亡敌人的测试。
2. 统一致死命中反应顺序，覆盖充能目标被雷电击杀、寒冷目标被强力攻击击杀、火焰致死传火；确保目标死亡只处理一次。
3. 调整备用栏的原子替换顺序，覆盖满栏且取出项位于首、中、末的位置；修复技能描述使用最终参数。
4. 约定有效伤害与溢出伤害的统计口径，并测试低生命目标；核查传火与状态来源的归因。
5. 更新现有依赖旧行为的测试，运行全量测试和构建检查。测试描述明确区分设计改变和回归。

### 阶段 1：迁移动作与描述

1. 从现有 `ACTION_IMPL` 中提取三个处理器，统一注册和校验；迁移 `castDueSkills`，暂时保留飞弹的原更新入口。
2. 将动作和修饰描述数据由最终计划提供，删除未知类型默认当冲击的分支；核对扩大前后的冷却与范围。
3. 逐个比对基线事件、目标选择和技能时间，允许的差异仅限阶段 0 明确修复项。
4. 更新构建器并验证打包结果；未知处理器应在启动或编译时失败，不能静默跳过施放。

### 阶段 2：迁移飞弹并引入御剑

1. 实现实体注册、创建、固定步更新、碰撞及清理；将现有 `projectiles` 访问逐步迁移，保留客户端渲染所需只读数据。
2. 先在相同构筑与输入下验证飞弹轨迹、目标失效、生命周期、伤害和事件；避免同时改平衡。
3. 新增御剑动作和环绕实体，先只支持无属性、无修饰；验证环绕、连续接触间隔、边界、销毁与数量上限。
4. 再接入火冰雷和已明确兼容的修饰；对未定义语义的组合禁止装配。测试改装后旧飞剑保持快照，新飞剑使用新计划。

### 阶段 3：移动策略与挥斩

1. 从 `playerMove` 提取现有行为，先以兼容策略复现基线，再引入接近、保持距离和自动。
2. 新增扇形挥斩：定义朝向、距离、角度、目标数量、强力标签和冷却；近战无目标时角色应能靠近后施放。
3. 以挥斩、飞弹及混合构筑验证策略；分别覆盖无目标、墙边、敌人重叠、目标切换与连续运行无抖动或越界。
4. 将位移请求作为独立步骤实现；突进内容可在后续阶段引入，不与普通移动争抢状态。

### 阶段 4：兼容矩阵与第二类持续行为

1. 为每个动作列出属性、修饰、反应兼容矩阵；合法项测试真实行为，非法项测试编译拒绝及 UI 提示。
2. 将分裂、回响、扩大、牵引逐步迁入修饰阶段处理器；固定触发次数与事件顺序，避免迁移改变现有伤害。
3. 实现一个陷阱：保存有效时间和触发次数，靠近时提交命中并清理；验证不同于御剑的等待触发生命周期。
4. 如要实现召唤，另行定义所有权、受击、存续、上限和目标失效策略；不将其假定为现有陷阱的简单参数变体。

### 阶段 5：风格、存档和 UI

1. 注册起始风格；新一轮创建构筑时使用选中风格，战斗中不因改变显示主题覆盖构筑。
2. 增加风格选择与移动策略入口；升级界面基于相同编译结果展示合法位置与最终描述。
3. 按第 16 节实现存档迁移、回退和提示；运行客户端接入测试、构建检查和真实侧栏交互验证。
4. 验证第二种复用现有行为的风格不需要新增战斗核心分支；记录实际修改文件作为扩展性验收证据。

## 16. 存档迁移与失败处理

当前客户端使用 `dsh.pet.v4.`，构筑另有自身版本号。引入风格时新增账户存档版本，例如 v5；**账户版本和构筑版本分别迁移**。首次读取时优先读取 v5；没有 v5 才读取 v4，保留原 v4 数据，生成并校验 v5 后写入新键。迁移失败或写入失败不得删除或覆盖原存档，并向用户显示可理解的提示。

v4 已有构筑应原样保留并经现有修复/编译流程验证；不得因设定默认风格而替换玩家技能。为迁移账户设置与当前移动行为相容的默认策略，并记录默认风格；新玩家再使用新的起始选择。重复加载必须幂等，不重复转换。未知风格降级为默认风格并保留合法构筑；未知组件按修复策略处理并提示。测试正常迁移、重复加载、数据损坏、未知 ID、写入失败及旧键仍可恢复。

现有账户存档主要保存构筑与进度而非完整战斗中间状态；本次不新增中途恢复战斗的承诺。若未来要持久化实体及计划快照，需另行设计版本化序列化、重编译和恢复时序，不能序列化函数或依赖当前内存对象。

## 17. 验证矩阵与完成定义

| 范围 | 必测场景 |
|---|---|
| 编译与兼容 | 所有注册组件有处理器；合法组合正常编译，非法组合有可读错误；描述对应最终数值 |
| 动作与实体 | 挥斩、飞弹、御剑、陷阱各自的创建、命中、冷却、清理和目标失效；同目标命中间隔 |
| 状态与反应 | 火冰雷跨动作复用；致死反应、连续传火、连锁终止与伤害归因 |
| 构筑编辑 | 空槽、替换、满备用栏、旧实体快照、新施放计划和升级候选 |
| 移动 | 三种策略、近远混合、边界、没有目标、位移竞争与失败冷却 |
| 可复现 | 同一 seed、初始状态、固定步与输入序列得到相同状态和事件；客户端固定步驱动与测试一致 |
| 集成 | v4 到新版本迁移、失败回退、生成客户端、侧栏显示与交互、模拟器与实际规则一致 |
| 性能 | 密集敌群和实体上限下测量耗时、数量与诊断；先记录设备和基线，再确定预算，不虚构固定阈值 |

每阶段至少运行对应测试、`npm test` 和 `npm run build:check`；源模块变化后先执行 `npm run build` 再检查生成结果。涉及交互或渲染的阶段进行实际侧栏验证。全量验收还包括：实现一个复用现有动作的额外风格，记录所需代码变更；它不应要求修改 `arena.js`、命中结算或其他动作处理器。首次实现全新行为可新增处理器和注册，但不应复制属性、反应与伤害规则。
